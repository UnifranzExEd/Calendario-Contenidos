================================================================================
  1. ARQUITECTURA GENERAL DEL SISTEMA
================================================================================

El sistema tiene DOS tipos de acceso:

  ┌────────────────────────────────────────────────────────────┐
  │  TIPO A: Acceso con sesión (usuarios internos)             │
  │  → Requiere login en index.html                            │
  │  → Cookies de sesión PHP                                   │
  │  → Accede a contenidos.php, campos.php, dropdowns.php, etc.│
  └────────────────────────────────────────────────────────────┘

  ┌────────────────────────────────────────────────────────────┐
  │  TIPO B: Acceso con API Key (sistemas externos)            │
  │  → No requiere login                                       │
  │  → Parámetro ?api_key=TU_CLAVE en la URL                  │
  │  → Accede a organicos.php, stats.php, microtareas.php      │
  └────────────────────────────────────────────────────────────┘

FLUJO DE DATOS:
  Base de datos MySQL
       ↓
  APIs PHP (/api/*.php)
       ↓
  JSON de respuesta
       ↓
  Frontend (dashboard.html / app.js)
  — o —
  Herramientas externas (Make, n8n, Python, apps móviles, etc.)


================================================================================
  2. BASE DE DATOS — ESTRUCTURA DE TABLAS CLAVE
================================================================================

── TABLA: contenidos ──────────────────────────────────────────────────────────
  Tabla principal. Un registro = una pieza de contenido en el calendario.

  COLUMNA               TIPO          DESCRIPCIÓN
  ──────────────────    ──────────    ──────────────────────────────────────
  id                    INT (PK)      Identificador único
  pestana_id            INT (FK)      A qué pestaña pertenece (redes, pauta...)
  tema                  TEXT          Título/tema del contenido (campo principal)
  idea                  TEXT          Descripción extendida o idea del contenido
  fecha                 DATE          Fecha de publicación planificada (YYYY-MM-DD)
  mes                   VARCHAR       Mes en mayúsculas (ENERO, FEBRERO, etc.)
  anio                  INT           Año (2026, 2027...)
  semana                INT           Número de semana del año
  red_social            VARCHAR       Instagram, Facebook, TikTok, YouTube...
  formato               VARCHAR       Post, Reel, Carrusel, Story, Video...
  estado                VARCHAR       Ver sección de ESTADOS más abajo
  prioridad             VARCHAR       Alta / Media / Baja (default: Media)
  buyer                 VARCHAR       Segmento de audiencia o buyer persona
  pilar                 VARCHAR       Pilar de contenido (Educativo, Emocional...)
  carrera               VARCHAR       Carrera universitaria relacionada
  enviar_postproduccion TINYINT(1)    1=Sí mandar a post-producción, 0=No
  postproductor_id      INT (FK)      Usuario encargado de post-producción
  enlace_contenido      TEXT          Link del archivo de producción (Drive/etc.)
  enlace_publicado      TEXT          Link del post ya publicado
  enlace_diseno         TEXT          Link del archivo de diseño final
  creado_por            INT (FK)      ID del usuario que creó el registro
  actualizado_por       INT (FK)      ID del último usuario que editó
  created_at            DATETIME      Fecha de creación automática
  deleted_at            DATETIME      NULL=activo, fecha=eliminado (soft delete)

── ESTADOS VÁLIDOS ─────────────────────────────────────────────────────────────
  Los estados siguen este flujo de producción:

  En elaboración  →  Redacción  →  En revisión  →  Producción
       →  Corrección  →  Aprobado  →  Programado  →  Publicado

  GRUPOS DE ESTADO (para la lógica de orgánicos y stats):
  • EN ESPERA:  'En elaboración', 'Redacción'
  • EN PROCESO: 'En revisión', 'Producción', 'Corrección', 'Programado'
  • HECHOS:     'Aprobado', 'Diseñado', 'Listo', 'Por publicar'
  • PUBLICADO:  'Publicado'  ← El único estado final "hecho"

── TABLA: pestanas ─────────────────────────────────────────────────────────────
  Las "pestañas" son las categorías o secciones del calendario.

  id, nombre (texto visible), slug (identificador URL), color, enlace_carpeta_base

  Slugs comunes: pauta, redes, instagram, facebook, tiktok, youtube

── TABLA: contenido_detalle ────────────────────────────────────────────────────
  Datos extra de cada contenido (copies para redes).
  Relación 1:1 con contenidos.

  contenido_id, copy_facebook, copy_instagram, copy_tiktok

── TABLA: microtareas ──────────────────────────────────────────────────────────
  Tareas internas del equipo (independientes del calendario de contenidos).

  id, titulo, descripcion, responsable_id, proyecto_id, fecha_entrega,
  prioridad (Alta/Media/Baja), estado (Pendiente/En proceso/Completada),
  creado_por, created_at, updated_at, deleted_at

── TABLA: microtareas_items ────────────────────────────────────────────────────
  Checklist de subtareas de cada microtarea.

  id, microtarea_id (FK), texto, completada (0/1), created_at

── TABLA: usuarios ─────────────────────────────────────────────────────────────
  id, nombre, email, password (hash bcrypt), rol, avatar, activo

  Roles disponibles: admin, community, postproductor

── TABLA: metricas ─────────────────────────────────────────────────────────────
  Métricas de rendimiento de contenidos ya publicados.

  contenido_id, espectadores, likes, comentarios, compartidos,
  guardados, alcance, clics, fecha_registro

  4. API DE ORGÁNICOS — Flujo de trabajo principal
================================================================================

  ENDPOINT:  GET https://organicos.page.gd/api/organicos.php
  KEY:       ?api_key=sk_org_8ef6ff5016983759f95810c5f70e582f
  CORS:      Habilitado (*) — se puede llamar desde cualquier dominio

── ¿QUÉ DEVUELVE? ──────────────────────────────────────────────────────────────

  Agrupa los contenidos por PERSONA ENCARGADA y FECHA DE ENTREGA.
  Para cada grupo, cuenta cuántos están "hechos" y cuántos "no hechos".

  Un contenido se considera HECHO si su estado está en:
    ['Publicado', 'Aprobado', 'Diseñado', 'Listo', 'Por publicar']

  Un contenido se considera NO HECHO si está en:
    ['En elaboración', 'Redacción', 'En revisión', 'Producción', 'Corrección']

── PARÁMETROS DE FILTRO ────────────────────────────────────────────────────────

  PARÁMETRO     EJEMPLO         DESCRIPCIÓN
  ─────────     ───────         ─────────────────────────────────────────────
  mes           AGOSTO          Mes en mayúsculas (default: mes actual)
  anio          2026            Año (default: año actual)
  responsable   nombre_persona  Filtra por nombre de persona encargada
  pestana       pauta           Filtra por slug de pestaña

── EJEMPLOS DE USO ─────────────────────────────────────────────────────────────

  # Orgánicos del mes actual
  GET /api/organicos.php?api_key=KEY

  # Orgánicos de agosto 2026
  GET /api/organicos.php?api_key=KEY&mes=AGOSTO&anio=2026

  # Solo los de una persona
  GET /api/organicos.php?api_key=KEY&responsable=Carla&mes=AGOSTO

  # Solo de la pestaña "redes"
  GET /api/organicos.php?api_key=KEY&pestana=redes&mes=AGOSTO

── VISTA KANBAN (cómo se usa en el dashboard) ──────────────────────────────────

  El frontend toma el array "data" de action=list y lo divide en 3 columnas:
    • Columna PENDIENTE:  items donde estado === "Pendiente"
    • Columna EN PROCESO: items donde estado === "En proceso"
    • Columna COMPLETADA: items donde estado === "Completada"

  La barra de progreso de cada card se calcula:
    progreso = (checklist.filter(i => i.completada == 1).length / checklist.length) * 100

  El indicador de color de prioridad:
    Alta  → Color rojo   (#ef4444) → borde superior de la card
    Media → Color naranja (#f59e0b)
    Baja  → Color azul   (#6366f1)

  Los filtros de prioridad funcionan en el frontend (no requieren nueva llamada API):
    mtState.prioFilter === 'Todas' ? mostrar todo : filtrar por prioridad

  7. SISTEMA DE PRIORIDADES
================================================================================

── PRIORIDADES DE CONTENIDOS (tabla contenidos) ────────────────────────────────

  PRIORIDAD   COLOR SUGERIDO   DESCRIPCIÓN
  ─────────   ─────────────    ─────────────────────────────────────────────
  Alta        Rojo #ef4444     Urgente. Publicación inminente o estratégica.
  Media       Naranja #f59e0b  Normal. La mayoría de los contenidos.
  Baja        Gris #6b7280     Secundario. Sin urgencia temporal.

  DEFAULT: Media (si no se especifica al crear)

  En el campo "prioridad" de la BD el valor es VARCHAR: 'Alta', 'Media', 'Baja'

── PRIORIDADES DE MICROTAREAS ──────────────────────────────────────────────────

  Los mismos 3 niveles: Alta / Media / Baja

  Orden de visualización en el Kanban:
    Las microtareas se ordenan: Alta primero → Media → Baja
    (ORDER BY CASE prioridad WHEN 'Alta' THEN 0 WHEN 'Media' THEN 1 ELSE 2 END ASC)

  Dentro del mismo nivel de prioridad, se ordenan por fecha_entrega ASC
  (los más urgentes primero, los sin fecha al final)

── CÓMO USAR PRIORIDADES PARA ALERTAS ──────────────────────────────────────────

  Regla de negocio sugerida:
    • Si hay más de 3 piezas de prioridad ALTA sin publicar → alerta roja
    • Si el porcentaje_completado de orgánicos baja de 50% → alerta naranja
    • Si una microtarea de prioridad Alta lleva más de 3 días sin moverse → alerta

  Consulta para monitoreo:
    GET /api/stats.php?action=piezas_por_prioridad&mes=AGOSTO&api_key=KEY
    → Revisar: data.prioridades[0] (Alta) → buscar estados != Publicado

  8. BARRA DE NOTIFICACIONES
================================================================================

── ¿QUÉ ES? ────────────────────────────────────────────────────────────────────

  El dashboard interno tiene una campana 🔔 en la barra superior.
  Al hacer clic, muestra un panel con notificaciones del sistema y un
  mini-dashboard de KPIs del mes actual.

── FUENTES DE DATOS ────────────────────────────────────────────────────────────

  1. NOTIFICACIONES DE ACTIVIDAD (tabla: notificaciones)
     → Se generan automáticamente cuando un usuario:
        - Crea un contenido nuevo
        - Cambia el estado de un contenido
        - El sistema detecta contenidos listos para publicar

     Tipos de notificaciones:
        nuevo_contenido   → Alguien creó nuevo contenido
        estado_cambio     → Un contenido cambió de estado
        (extensible)

  2. ALERTA DE PENDIENTES (endpoint: /api/contenidos.php?action=notifications)
     → Cuenta los contenidos en estado Listo/Por publicar/Aprobado
        con fecha <= hoy que aún no están publicados.
     → Respuesta: { "success": true, "count": 3 }

  3. KPIs DEL MES (endpoint: /api/contenidos.php?action=piece_stats)
     → Devuelve conteos del mes actual:
        total, en_espera, en_proceso, hechas, publicadas, by_red, by_prioridad

── LÓGICA DEL CONTADOR DE LA CAMPANA ───────────────────────────────────────────

  El número que aparece en el badge de la campana es:
    (notificaciones no leídas) + (contenidos pendientes de publicar)

  El frontend consulta esto periódicamente (cada X minutos) o al cargar la página.

── CÓMO REPLICAR LA BARRA DE NOTIFICACIONES ────────────────────────────────────

  En tu proyecto nuevo:

  1. Crea la tabla notificaciones:
     CREATE TABLE notificaciones (
       id          INT AUTO_INCREMENT PRIMARY KEY,
       usuario_id  INT NOT NULL,
       tipo        VARCHAR(50),
       mensaje     TEXT,
       contenido_id INT DEFAULT NULL,
       leida       TINYINT(1) DEFAULT 0,
       created_at  DATETIME DEFAULT CURRENT_TIMESTAMP
     )

  2. En tus APIs (al cambiar estados, crear items), llama a:
     crearNotificacion($usuario_id, 'tipo', 'mensaje', $contenido_id)
     — o —
     notificarRol('admin', 'tipo', 'mensaje', $contenido_id)

  3. En el frontend, consulta periódicamente:
     GET /api/notificaciones.php?action=count  → { count: N }
     GET /api/notificaciones.php?action=list   → [ ...últimas notifs... ]

  4. Al hacer clic en una notificación:
     POST /api/notificaciones.php?action=mark_read  { id: N }

── PASO 4: PATRÓN DE AUTENTICACIÓN MIXTA ──────────────────────────────────────

  Para que un endpoint funcione tanto con sesión como con API Key
  (como microtareas.php), usa este patrón:

  $user = null;
  $providedKey = $_GET['api_key'] ?? '';
  if (!$providedKey) {
      $authHeader = $_SERVER['HTTP_AUTHORIZATION'] ?? '';
      if (preg_match('/Bearer\s+(.+)/i', $authHeader, $m)) {
          $providedKey = $m[1];
      }
  }
  if ($providedKey) {
      if ($providedKey !== ORGANICOS_API_KEY) {
          http_response_code(401);
          echo json_encode(['error' => 'API Key inválida']);
          exit;
      }
      $user = ['id' => 0, 'nombre' => 'API', 'rol' => 'admin'];
  } else {
      $user = requireAuth(); // Redirige a login si no hay sesión
  }

── PASO 5: PATRÓN DE RESPUESTA JSON ESTÁNDAR ──────────────────────────────────

  En database.php, implementar estas helpers:

  function jsonResponse($data, $code = 200) {
      http_response_code($code);
      header('Content-Type: application/json; charset=utf-8');
      echo json_encode($data, JSON_UNESCAPED_UNICODE);
      exit;
  }

  function getJsonInput() {
      $input = json_decode(file_get_contents('php://input'), true);
      return $input ?: [];
  }

  Siempre responder con:
    Éxito:  { "success": true,  "data": ... }
    Error:  { "success": false, "error": "mensaje" }

── PASO 6: PATRÓN SOFT DELETE ─────────────────────────────────────────────────

  Nunca borrar registros de la BD. Usar deleted_at:

  -- Para "eliminar":
  UPDATE microtareas SET deleted_at = NOW() WHERE id = ?

  -- Para listar (excluir eliminados):
  WHERE deleted_at IS NULL

  -- Para restaurar:
  UPDATE microtareas SET deleted_at = NULL WHERE id = ?

── PASO 7: CORS PARA APIs PÚBLICAS ────────────────────────────────────────────

  Al inicio de cada API pública, agregar:

  header('Content-Type: application/json; charset=utf-8');

  header('Access-Control-Allow-Methods: GET, POST, OPTIONS');
  header('Access-Control-Allow-Headers: Authorization, Content-Type');
  if ($_SERVER['REQUEST_METHOD'] === 'OPTIONS') {
      http_response_code(200); exit;
  }
